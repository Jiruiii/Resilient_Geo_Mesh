# 政府公告本機即時呈現與 Mesh／雲端傳播規格

**狀態：設計已確認並執行；Android 實機驗收待完成**

**相關既有設計：** [`2026-10-12-government-device-mesh-warning-design.md`](2026-10-12-government-device-mesh-warning-design.md)

## 目標

政府 Android 手機建立公告後，該公告應立即成為本機已驗證官方事件並出現在通知介面，不需先執行「政府資料更新」或從雲端下載。若緊急模式已啟用，手機應立即將新公告納入 Mesh 傳播；網路可用時，公告應自動補傳雲端，讓其他手機和 Web 經由已簽章的政府 feed 接收。

## 使用者已確認的產品規則

- 公告建立成功後先寫入本機，再分別嘗試 Mesh 傳播與雲端補傳；任何一條傳播路徑失敗都不能撤銷本機公告。
- 只有緊急模式已啟用時才使用 Mesh。若未啟用，保留本機公告並提示使用者可啟用緊急模式；不得自動開啟無線電或緊急模式。
- Web 不使用 BLE Mesh。Web 透過中央簽章的政府 feed 接收及驗證公告。
- Mesh 狀態只能反映本機或已觀察到的傳輸狀態；沒有接收端確認時，不得宣稱其他手機已收到。

## 已查證現況與待解問題

- Android 政府工作台已呼叫原生建立流程。原生端會簽署公告，驗證事件與 chunk，並在同一 Room 提交流程寫入事件、Mesh chunk 和雲端 outbox。
- 原生事件儲存已有 Flutter 初始資料與事件串流；通知篩選允許已驗證的 `official.announcement`／`GOVERNMENT` 事件。因此架構上已有本機資料來源。
- 現有 Mesh 引擎會在同步時公布本機 chunk inventory，但同步冷卻時間為 60 秒。公告新增目前沒有明確的即時同步觸發規格。
- 雲端補傳 outbox 已存在；目前 Flutter 工作台在刷新後及工作台開啟期間每 5 分鐘嘗試補傳。Android 的網路背景工作目前負責下載 feed。尚未確認網路恢復時背景上傳能即時執行。
- 使用者回報「必須執行政府資料更新才會在建立者手機看到公告」，與上述本機資料路徑不一致。此執行期問題尚未在本環境重現；目前沒有 `adb` 或連線中的 Android 手機，根因須在實作與裝置驗收時確認。

## 預期資料流程

### 1. 建立者手機本機呈現

1. Android 政府使用者送出公告。
2. 原生端沿用既有政府設備憑證和事件簽章驗證；以同一個 event id 產生官方事件與 Mesh chunk。
3. Room 原子保存事件、chunk 和待上傳狀態。
4. 儲存成功即透過既有事件串流更新 Flutter 地圖／通知資料。公告立刻顯示為已驗證官方公告，不等待 API、中央 feed 或「政府資料更新」。
5. 工作台可更新狀態，但不得以等待雲端清單重新載入作為本機公告出現的必要條件。

### 2. Mesh 傳播

- **緊急模式已開啟：** 新 chunk 寫入後立即通知現行 Mesh 同步流程刷新本機 inventory 並安排傳輸；不可只等待既有 60 秒週期自然到期。若目前正有同步工作，該工作完成後的新 inventory 必須包含公告。重試仍遵循現有連線失敗與併發限制。
- **緊急模式未開啟：** 公告仍可建立並留在本機。工作台顯示 Mesh 尚未啟動及啟用緊急模式的操作提示；不自動啟動服務或無線電。
- 對端也必須啟用 Mesh 並可連線才會收件。無可用對端時保持待同步狀態；只有現有傳輸結果能證明收到時，才顯示對端已收到。
- 透過網路 feed 收到的已驗證 chunk，若本機緊急模式已啟用，也納入後續 Mesh inventory，讓接收手機可繼續轉傳。

### 3. 雲端補傳與其他裝置接收

- 原始簽章事件及 event id／payload hash 不因重試而改變。離線或上傳失敗時，Room outbox 保留待上傳資料。
- 有網路且政府工作階段有效時，自動嘗試補傳；觸發點至少涵蓋公告建立後、網路恢復、App 回到前景，以及既有背景網路同步工作。使用者不需手動執行「政府資料更新」來上傳。
- API 維持以 event id 與 payload hash 冪等處理重試。成功上傳後，狀態先顯示等待正式 feed 發布；中央發布完成並由簽章 feed 證實後，才顯示已發布。
- 其他 Android 手機及 Flutter Web 透過中央簽章 feed 下載及驗證同一公告。Android 將已驗證事件寫入本機事件庫；Web 維持現有 feed 接收流程。若 Android 接收端已啟用緊急模式，接收事件也可進入 Mesh 轉傳。
- 背景排程受 Android 系統執行時機、有效登入工作階段及網路狀態限制；介面不可承諾即時雲端發布。前景及重新開啟 App 時仍需重試未完成項目。

## 狀態與錯誤呈現

| 條件 | 本機公告 | 建立者狀態與行為 |
|---|---|---|
| Room 驗證及提交成功 | 立即顯示 | 已儲存於本機 |
| 緊急模式開啟且尚未有接收確認 | 顯示 | Mesh 同步中／等待可用裝置；不得宣稱已送達 |
| 緊急模式關閉 | 顯示 | Mesh 未啟用，提供啟用緊急模式的提示 |
| 離線或雲端補傳失敗 | 顯示 | 待雲端補傳；保留 outbox 並自動重試 |
| API 接受但尚未進入公開 feed | 顯示 | 等待官方 feed 發布 |
| 簽章 feed 已發布且客戶端已確認 | 顯示 | 已發布 |
| 簽章、憑證、撤銷或內容驗證失敗 | 不得以已驗證官方公告顯示或轉傳 | 顯示可理解的錯誤；保留必要診斷資訊，不偽報成功 |
| Room 寫入失敗 | 不顯示成功公告 | 告知建立失敗；不可回報已儲存、Mesh 或已上傳 |

## 安全與相容性約束

- 沿用既有政府設備憑證、事件／chunk 驗證、撤銷快取與正式 feed 簽章規則；不得放寬 `device:` 金鑰的事件授權範圍。
- Mesh 和雲端傳輸使用同一個簽章事件及 event id。feed 接收與 Mesh 轉傳不得改寫原始事件簽章內容。
- 同一 event id、相同 payload 的本機重送、Mesh 接收及 feed 接收必須冪等；同 id 不同 payload 仍視為衝突並拒絕。
- 保留緊急模式作為 Mesh 的明確使用者控制；本規格不授權自動啟動 Mesh。
- Flutter Web 與 Android 必須維持相同公告資料、官方驗證結果、通知呈現及載入／錯誤語意。Web 的 BLE 不適用已由使用者確認，Web 以簽章 feed 為接收方式。

## 驗收情境

1. Android 政府使用者建立有效公告後，建立者手機在無網路狀態下立即看到通知；不執行政府資料更新、不連接雲端亦成立。
2. App 重新開啟後，Room 中的公告仍立即出現，且不重複建立第二筆事件。
3. 緊急模式已開啟且對端可連線時，新公告觸發 Mesh inventory 更新並傳至相容對端；若無對端，介面不宣稱送達。
4. 緊急模式關閉時，公告仍本機可見，出現啟用提示，服務及無線電保持關閉；使用者啟用後，公告可進入 Mesh 同步。
5. 補傳失敗或裝置離線時，outbox 保留原 event id 和 payload hash；網路恢復或 App 回前景後自動重試，不需點「政府資料更新」。相同事件重試不產生重複公告。
6. 補傳成功但 feed 尚未發布時，工作台顯示等待發布；正式簽章 feed 更新後，Web 與其他 Android 手機顯示相同公告與驗證結果。
7. 其他 Android 手機從簽章 feed 收到公告後，在本機立即顯示；其緊急模式開啟時可再透過 Mesh 轉傳。
8. Web 只透過簽章 feed 顯示公告，驗證失敗時不把該事件標示為政府已驗證。
9. 政府工作台、通知畫面、Web feed、Flutter Android 共用狀態和錯誤文字一致；下載 feed 的既有「政府資料更新」仍可供手動刷新，但不再是公告本機顯示、Mesh 傳播或雲端補傳的前置條件。

## 本規格不涵蓋

- 改變緊急模式的啟用規則、Mesh 無線電平台範圍或既有設備憑證信任模型。
- 將 Web 改造成離線政府公告簽署端或 Web BLE Mesh 節點。
- 改變公告內容欄位、官方查證語意、事件有效期限或中央發布簽章責任。
- 宣稱 Android 背景工作能繞過系統排程限制或保證即時上傳。
