# 決賽實測計畫（草案）

目的：決賽前補齊「真機、真環境、有次數」的數據，讓評審看到系統在什麼條件下能用、在哪裡會失效。現有數據多半是同房間、亮屏、1–2 片資料的流程驗證，證明「做得到」，還不足以回答「多遠、多快、多久、多可靠」。

## 共同規則

- **每個條件至少 5 次**，成功率題目至少 20 次。報告寫 n、成功率、中位數（p50）與 p95，失敗案例和原因也要列出，不只挑成功的。
- **記錄條件**：機型、Android 版本、電量、室內／室外、距離、障礙物、螢幕亮或鎖、是否插 USB、日期時間。
- **不插 USB 量耗電**：09-05 那組 22 mW 就是插電量到雜訊而作廢。
- **手機離開 Wi-Fi**：災害現場沒有路由器。兩台若連同一個 Wi-Fi，Nearby 可能改走路由器，數字會偏好。測前讓手機忘記網路或關掉路由器／熱點，行動數據也關掉（第 14 項 Web 端除外）。
- **留證據**：每組拍一段影片（兩台手機同框加上計時），並保存 log 或 timeline 截圖，放在 `docs/adr/evidence/`。
- **統一計時點**：
  - 開始同步：按下開始的時間。
  - 發現：看到對方的時間。
  - 建連：連線成功的時間。
  - 完成：最後一片套用的時間。
  - 畫面更新：路線改推薦的時間。
- 結果統一記成 CSV（量測模式自動產生，欄位見文末〈工具〉提到的文件），方便直接畫圖，也能回填模擬器。

## P0：決賽一定要有

### 1. 傳輸距離（三種傳輸分開測）

| 項目 | 設定 |
| --- | --- |
| 距離點 | 1、3、5、10、15、20、30、50 公尺，之後每 10 公尺往外，直到連續 3 次失敗 |
| 環境 | ① 室外空曠（操場）② 室內走廊直線 ③ 隔一道牆 ④ 跨一層樓 ⑤ 手機放口袋或背包 |
| 傳輸 | BLE、Nearby、Wi-Fi Direct：用強制單一傳輸的方式各測一輪，最後再用「自動」測一輪 |
| 每點量 | 成功與否、發現時間、建連時間、完成時間、BLE RSSI |
| 交付指標 | 有效距離：成功率 ≥ 80% 的最遠距離。另畫「距離 vs 成功率」與「距離 vs 完成時間」兩張圖 |

注意：手機拿在約 1 公尺高、螢幕朝同方向，距離用捲尺或雷射測距儀量，不要用目測。

### 2. 資料量與速度（傳輸量／吞吐量）

量測模式提供的級距：

| 級距 | 意義 |
| --- | --- |
| 1 片 | 單筆回報或避難所狀態，對照現有數據 |
| 約 50 KB（20 片） | 一小區的更新 |
| 約 1 MB（157 片，約 1.7 MB） | 對照 BLE 舊量測，也接近舊內湖資料集（183 片，約 1.18 MB）的量級 |
| 約 10 MB（168 片） | 只測 Nearby 和 Wi-Fi Direct |
| 全部（203 片，約 39 MB） | 「第一次見面要多久才能拿到全台災害資料」，只測 Nearby 和 Wi-Fi Direct |

- 三種傳輸都測，距離固定在 1 公尺和 10 公尺。
- 交付指標：KB/s，以及完整資料集需要幾秒。
- 目前最大的空白：Nearby 和 Wi-Fi Direct 從未量過大資料的吞吐量。BLE 傳「約 1 MB」級距（約 1.7 MB）估計要 7 分鐘左右；如果 Wi-Fi Direct 傳全部 39 MB 只要幾十秒，這會是很有說服力的對比。

### 3. 發現與連線可靠度（重複相遇）

- 每種傳輸做 20 次「分開 → 重新靠近」：兩台手機先遠離到看不到彼此，再靠回 3 公尺。
- 交付指標：
  - 成功率。
  - 發現時間的 p50 和 p95。
  - 失敗原因分類：Samsung 邀請沒按、逾時、GATT 錯誤等。
- 一併記錄第二次相遇「不重傳」的次數比例。

### 4. 鎖屏與背景（Doze）

- 兩台都開緊急模式後鎖屏，分別放 5、15、30、60 分鐘後再靠近，不解鎖，看資料會不會自己傳過去。
- 交付指標：各時間點的成功率、從靠近到收到的時間。
- 重要性：真實災難時手機在口袋裡，評審一定會問。目前只有「沒有前景服務、鎖屏時 0/19」這筆反例，還沒有「有前景服務、鎖屏時成功」的正面數據。
- Samsung 的 Wi-Fi Direct 邀請在鎖屏時沒人能按，要特別記錄它在鎖屏下的表現。

### 5. 耗電（拔線、長時間）

| 情境 | 時長 | 量法 |
| --- | --- | --- |
| 基準：App 關閉、螢幕關 | 2 小時 | 電量 % 變化，加上 `dumpsys batterystats` |
| 緊急模式待命（BLE 掃描 + 高速傳輸輪替） | 2–4 小時 | 同上 |
| 緊急模式加上每 10 分鐘一次同步 | 2 小時 | 同上 |

- 交付指標：每小時耗電 %，以及「滿電可撐幾小時」。
- 量測條件：亮度和網路狀態固定，測前充到 100% 再拔線。
- 舊數據 +54 mW 只包含 BLE 廣播加掃描，現在還多了 Nearby 和 Wi-Fi Direct 輪替，要重測。

### 6. 三台接力（Store-Carry-Forward）

- 情境：A 有新資料；B 先遇到 A，再走到遠處遇到 C；C 從沒和 A 見過面。
- 交付指標：
  - C 是否收到。
  - 資料從 A 發布到 C 畫面改推薦，總共花多久。
  - 中間各段的時間。
- 這是「網狀擴散」的核心證明，目前完全沒做。至少要做 5 輪。

### 7. 完整情境重複（避難所額滿改道）

- 現有兩機離線演練只各做過一兩次。這次重複 10 次，A、B 角色和機型對調。
- 交付指標：成功率，以及從「A 發布 FULL」到「B 畫面改推薦 A」的總時間（p50、p95）。

## P1：有餘力就做，能加分

### 8. 走路錯身（真實接觸窗）

- 兩人以正常步速（約 1.2 m/s）面對面走過，從 50 公尺外開始，錯身後繼續走到 50 公尺外。
- 交付指標：一次錯身傳了多少片、多少 KB，以及哪種傳輸來得及。這比固定距離更貼近災害現場的情況。
- 另做「一人站著，一人走過」。

### 9. 機型相容

- 把手邊機型（Pixel 7、Pixel 8a、Samsung SM-A5360、Sharp SH-M32，如果可以再借 1–2 台中低階機和不同品牌）兩兩配對，每對至少做一次完整同步。
- 交付指標：相容矩陣（✓／✗／需手動按邀請）。

### 10. 擁擠環境

- 在藍牙和 Wi-Fi 裝置很多的地方（教室、捷運站、賣場），重測第 1 項的 5、10 公尺點和第 3 項。
- 交付指標：和空曠處相比，成功率與時間差多少。

### 11. 多台同時

- 4–5 台同時開緊急模式擺在一起，其中一台有新資料。
- 交付指標：全部收到的時間、每台收到的順序。

### 12. 收到資料到畫面更新

- 從最後一片套用，到地圖改推薦或重新算路完成的延遲。
- 一併測飛航模式下路線計算的時間：已有 Pixel 8a 的 p95 38.5 ms，可再補一台中低階機。

## P2：展示用，做一次即可

### 13. 安全性

- 現場示範竄改一片資料（改內容或改簽章）、送出過期 TTL、送出非白名單來源，手機全部拒收。
- 交付內容：拒收計數截圖或影片。單元測試已經涵蓋這部分，這裡是為了讓評審看到。

### 14. Web 端

- Web 版不參與手機互傳，只量下載簽章資料的時間：在 Chrome DevTools 用 Fast 4G 和 Slow 3G 節流，量首次載入和資料更新的時間，以及總下載量。
- 用來說明「網路還在時 Web 也能拿到相同資料」。

## 量完之後

1. **回填模擬器**：`simulator/fixtures/sim-config.json` 的 `contact_probability`（0.55）和 `transfer_failure_prob`（0.06）目前是工程估計值。用第 3、8 項的實測成功率取代，`max_bytes_per_round` 用第 2 項的高速傳輸吞吐量更新，再重跑 `node simulator/cli.mjs matrix`。這樣「100 台手機的覆蓋率」就是以實測為基礎，而不是估計。
2. **一頁總表**：每種傳輸一列，欄位是有效距離、吞吐量、整份資料集時間、相遇成功率、鎖屏成功率、每小時耗電。這一頁就是決賽簡報的主圖。
3. **誠實列出限制**：失敗案例和沒測到的條件照實寫，評審通常更信任這樣的數據。

## 工具

| 工具 | 現況 |
| --- | --- |
| 距離、吞吐量、重複相遇、接力（第 1–3、6、8–11 項） | 量測畫面 `MeshMeasureActivity`（debug）：固定單一傳輸，可選 1 片到約 39 MB，每次試驗寫一列 CSV，含 RSSI 和各計時點 |
| 鎖屏、Doze、耗電、自動選擇（第 4、5、7 項） | debug 版同步頁的「量測紀錄」開關：正式緊急模式服務寫入每次同步結果，並每 5 分鐘記錄電量、螢幕與 Doze |
| BLE 傳輸方式的底層量測 | 既有的 `BleGattMeasurementActivity` |
| Web 下載時間（第 14 項） | Chrome DevTools 節流，不需要寫程式 |

操作步驟、CSV 欄位和限制，見 `docs/superpowers/plans/2026-10-30-measurement-mode.md`。
